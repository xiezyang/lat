The 23-byte clear function is the first TU candidate: one TB accounts for
99.27% of that function's dynamic executions; its `SUB RSI,1; JNE` loop
has a stable back edge. The 34-byte copy function is another compact candidate;
its `ADD RAX,1; CMP RAX,RDX; JNE` loop accounts for 86.42% of that
function's executions. The 845-byte fixed-point function is worth a separate
follow-up: its 27 TBs account for 4.69% of the IR2 weighting, but it has
multiple loops and much greater expected code size. Its hottest TB alone
accounts for 45.91% of that function's weighting, so specializing just that
TB is not equivalent to eliminating flags across its whole function.

In this recorded run, the clear entry TB ran 5,609 times and the loop TB
2,284,255 times (about 407 iterations per entry on average). The copy entry
ran 95,894 times and its loop TB 1,830,013 times (about 19 iterations per
entry). These are ratios of recorded TB execution counts, not a distribution
of actual call lengths; the loop TB may have been entered through other
paths.

The current source has opt-in TU ranges for the two short functions and an
opt-in no-LBT flag path. `ts_tu_same_region()` now excludes those two
functions from neighboring page-level TUs and keeps them separate from each
other. An O1/static/no-KZT LoongArch build with the existing configuration
completed on `192.168.8.23` in
`/home/yuerengan/xzy/xfyun-hot-tu-20260929/build64`. The
`192.168.8.200` machine is reserved by the user and must not be used.

After the first build, a flag-correctness review limited the no-LBT direct
branch optimization to the copy loop's `CMP; JNE` back edge. The `TEST` at
each function's entry now uses the normal translator, which preserves flags
when the length is zero. The copy loop calculates the final `CMP` flags on
fallthrough to `RET` and on the unlink fallback, but omits them on the
internal back edge. The clear loop retains its separate `SUB; JNE` fast
path with full flags on fallthrough and on unlink. This change was rebuilt
successfully on `192.168.8.23`; it is **not** a runtime correctness or
speed measurement. Final build SHA-256:
`3ee2949d3c904ee32663a42cd02886fb6febb7ac586281aeb7aa544e53706f4c`.

The collection loop was then corrected to stop at the *same function's*
range and require identical `cflags`. The clear and copy ranges are close
enough that collecting all consecutive "hot" TBs would otherwise mix them
into one TU. The corrected build completed on `192.168.8.23` with SHA-256
`7116d15f66161180526380dac89da09320923628a686dfb9ca1e95199d72ab54`.
TU formation and execution still need runtime evidence.

## Entire-function native TU and board measurements (2026-09-29)

The current `codex/no-lbt-recovery-20260919` source builds each measured
function as a separate four-TB TU. After checking the complete x86 byte
sequence and the four successor relationships, the entry `TEST/JE`, middle
`NOP` or `XOR/NOP`, byte-access loop and `RET` all use dedicated LoongArch
emission. The loop uses a direct native back edge instead of leaving and
re-entering the TB. `RET` still uses LATX's indirect return lookup to reach
the translated x86 caller; it cannot use an ordinary LoongArch `ret`.
Selection requires `LATX_XFYUN_HOT_TU=1`, `LATX_TU=1` and no LBT. The ELF
size/name and exact function bytes are checked; AOT automatically selects
and restores these TUs, without setting an AOT file path. There is no
separate EFLAGS switch.

The verified build on `192.168.8.23` is
`/home/yuerengan/xzy/xfyun-hot-tu-20260929/build64/latx-x86_64`, SHA-256
`ee415e9032d61ad05625421649d4d754596eb189e16fda25431800cac71d856e`.

SHA-256 `e0f9aeaf8619a87fa510ba8891138aa0bc19e1dd1d2d10c72b9c428cdb21348a`.
Generation logs showed each function's four dedicated TBs and a warm run
logged automatic AOT recovery for both four-TB TUs. The independent 35-case

`36a913ca4956f22ef245a80b802c4bc555eb86cddaf5d7522a5b0b29dd3265aa`.

On `192.168.8.200`, with the newer `libmsc.so` SHA-256

then faults during an intermediate copy iteration. On 23 a normally
translated run with `LATX_AOT=0` reports the expected guest instruction

it does not establish that the dedicated path introduced it. Conversely,
successful normal synthesis and the 35-case test do not prove this optimized
path correct under page faults. AOT/TU signal recovery must be fixed and
tested separately before claiming complete x86 exception semantics.

## Isolated function timings on board 200 (2026-09-30)

A small x86-64 caller invokes each exported `libmsc.so` function one million
times on a 32-byte buffer and checks the final buffer contents. The caller explicitly
reloads argument registers for every invocation: the clear function changes
`RSI`, so declaring it a read-only inline-assembly input would incorrectly
make almost all subsequent calls zero-length. All groups used the same
`/root/xzy/sdk-thread-board200-20260929/xfyun/libmsc.so` (SHA-256 above),
`LBT_X86=0 LATX_AOT=1 LATX_TU=1`, separate new `HOME` directories, and
no SDK debug logging. The ordinary AOT group **unset**
`LATX_XFYUN_HOT_TU`; defining the variable to the empty string still enables
the optimization because LATX tests its presence with `getenv()`.

The first two calls per group generated AOT and are excluded below. Logs for
runs 3-5 in each hotspot group explicitly record recovery of the selected
four-TB TU at `libmsc.so+0x1c8810` or `+0x1c8830`. The byte-only group uses
binary SHA-256 `e68b4f7f2ef49a5ebb747dd6d94feb617db554411cc3b8fcc7b34d9a0e24ac6f`;
the entire-function group uses the current binary SHA-256 above.

| 32 bytes, 1,000,000 calls; median of warm runs 3-5 (s) | Ordinary AOT | Byte-only hotspot TU | Entire-function native TU |
| --- | ---: | ---: | ---: |
| Clear | 1.511 | 1.060 | 1.054 |
| Forward copy | 2.300 | 1.985 | 1.979 |

The dedicated hotspot version is about 30% faster for clear and 14% faster

## Build-host clear-loop barrier experiment (2026-09-30)

On `192.168.8.23`, a temporary build used `dbar 0x0a` (store-to-store
ordering) after each byte store on the clear loop's internal back edge,
with `dbar 0` retained on its normal exit and TU-unlink exit. The copy
function was unchanged. Three whole XFYun runs with a fresh automatic AOT
cache returned the reference WAV SHA-256 above. The third run logged recovery
of both four-TB TUs. All 35 independent boundary cases matched the native
x86 reference output hash above.

Two separate warmed AOT homes and alternating runs on the build host compared
the experimental binary with the verified full-native binary. For 407-byte
clear calls repeated 120,000 times, the six-run medians were **0.49286 s**
with the original full barrier and **0.49355 s** with the narrower barrier;
ranges were 0.49221-0.49345 s and 0.49214-0.49514 s respectively. This
does not show a benefit. The change was removed, and the build on 23 was
restored to SHA-256 `ee415e9032d61ad05625421649d4d754596eb189e16fda25431800cac71d856e`.
No board-200 test was run for this experiment.

Another proposed experiment, omitting the copy loop's write-after barrier
and placing full barriers only at its exits, was rejected before building:
the next iteration can read an overlapping address before reaching either
exit. Exit-only barriers do not preserve the original load/store ordering.

## Copy-loop load barrier removal (2026-09-30)

The complete native copy TU now omits `dbar 0` immediately after the byte
load at `libmsc.so+0x1c8840`. The subsequent byte store consumes the loaded
register, and its existing full `dbar 0` still precedes the next loop
iteration's load. This preserves the read-to-write dependency and orders
successive iterations even when the source and destination overlap. The
ordinary TB translation retains both barriers. Shape and byte-sequence
checks restrict the change to the measured four-TB function TU; no new
runtime switch is needed.

The build on 23 passed three full syntheses with a fresh HOME, with the
reference WAV hash and explicit automatic recovery of both four-TB TUs on
the third run. The 35-case boundary test (including forward overlapping
copies) matched the native x86 reference hash. Repeating that standalone
test three times with the same HOME also matched, but its logs did **not**
report recovery of `libmsc.so`'s dedicated TU, so it does not independently
prove the overlapping cases executed from recovered AOT code.

On 23, after independent cache warmups and explicit recovery of the copy TU,
six alternating 32-byte copy comparisons at 700,000 calls took
0.444-0.448 s with the previous binary versus 0.268-0.269 s with the new
one. Four alternating 19-byte comparisons at one million calls took
0.386-0.387 s versus 0.236-0.237 s respectively.

The same 23-built experimental binary (SHA-256
`0dac5ba872179e0a9910589ec068a19b757b5b08fae979711e1bfbf7264e633a`)
was copied to board 200; the comparison used the same unchanged newer

from both groups confirmed automatic recovery of both four-TB TUs. Four
alternating 19-byte copy comparisons at one million calls were 1.211-1.213 s
with the stable full-native build and 0.757-0.758 s with the experimental

Six alternating whole-XFYun pairs on board 200, after three warmup runs

## Constant flags at the normal function exit (2026-09-30)

The two dedicated loops now directly write the arithmetic EFLAGS on their

## Native ivModDiffCoefFix support (2026-09-30)

`libmsc.so+0x1e0d70` (`ivModDiffCoefFix`) was selected as the next full
native-function candidate. The function is 90 bytes, has no calls, and executes
about 60,344 times per XFYun run. Its three input ranges and fixed-point
formula were checked exhaustively at every 16-bit gain for 13 boundary values,
plus 1,000,000 random value/gain pairs. The optimized path matched the dynamic
library function for every case.

Two implementations were tested. Calling a C helper through the AOT relocation
mechanism was slower than the existing TU because saving and restoring guest
state dominated the tiny function: 1 million calls took about 117 ms in the
old path and 138 ms with the helper. The final version instead expands the
complete function directly into LoongArch instructions in the TU, with no
helper call or guest-register save/restore. After removing the temporary
separate-TU regression, it runs 3 million calls in about 268 ms versus 350 ms
for the previous path, about 23% faster in the isolated benchmark.

An initial implementation also made this function a separate TU. That increased
instructions and slowed complete XFYun, so it was rejected. The final form
keeps the function in its original page-level TU and only replaces the entry
with the complete native body. With complete AOT caches, the whole-XFYun effect
is below run-to-run noise: hardware counters showed about 1% fewer instructions,
while cycle changes were smaller and inconsistent in direction. This is
consistent with the function's 0.903% total IR2 weighting. All complete runs
produced the reference WAV hash
`e0f9aeaf8619a87fa510ba8891138aa0bc19e1dd1d2d10c72b9c428cdb21348a`.

The final inline implementation is built into the branch commit for
`ivModDiffCoefFix`. A temporary `/tmp` exhaustion during later comparisons
made AOT publication fail and produced misleading 8.8 s results; after
cleaning `/tmp`, the persistent AOT path was restored and the measurements
above were repeated.
